# Windows notes

How Winlight uses the Windows display, power and session APIs, the design rules behind its reliability and safety, and what other projects' experience taught. It is written for contributors and for anyone diagnosing a problem on their own hardware.

Two mature, MIT-licensed tray apps shaped much of the Windows backend: [Monitorian](https://github.com/emoacht/Monitorian) (C#/WPF) and [Twinkle Tray](https://github.com/xanderfrangos/twinkle-tray) (Electron with native modules). Where a point comes from them, the source is named. No code is copied; the approaches are re-implemented in Python. [KWin](https://invent.kde.org/plasma/kwin) contributed the composition of brightness and color temperature, and [knighttime](https://invent.kde.org/plasma/knighttime) the night light schedule rules.

Paths are relative to `nightlight/`. Items still open are marked **Planned** or **Not planned**; everything else describes the current code.

## 1. Finding displays and telling them apart

No single API gives everything, so Winlight combines several, as both projects do:

| API | Gives | Used in |
|---|---|---|
| `QueryDisplayConfig` + `DisplayConfigGetDeviceInfo` | Each active path: source GDI name (`\\.\DISPLAY1`), EDID friendly name, device path, connector, HDR state | `hardware/win32.py` |
| `EnumDisplayMonitors` + `GetMonitorInfoW` | `HMONITOR` handles and their GDI names | `hardware/win32.py` |
| `GetPhysicalMonitorsFromHMONITOR` (dxva2) | DDC/CI handles, one per physical monitor | `hardware/win32.py` |
| `EnumDisplayDevices` | Older device list, used when `QueryDisplayConfig` fails | `hardware/win32.py` |
| WMI `root\wmi` `WmiMonitorBrightness(Methods)` | The laptop panel's brightness and supported levels | `hardware/windows.py` |

- **Names** come from the EDID through `QueryDisplayConfig`, never from the DDC/CI capabilities string, which is slow and can hang some monitors (Twinkle Tray, Monitorian).
- **Built-in and indirect displays** are told apart by connector type: LVDS, embedded DisplayPort and UDI are built-in panels; DisplayLink/USB, Miracast and virtual displays are "indirect" and have no DDC/CI channel, and are reported as such.
- **Identity.** A display's key is its EDID manufacturer and product code from the device path (`DEL41A2`), plus the serial number from the EDID Windows keeps in the registry (`HKLM\SYSTEM\CurrentControlSet\Enum\<instance>\Device Parameters\EDID`, read without talking to the monitor): `DEL41A2:7XKJ9F3`. Identical monitors therefore keep separate settings whichever port each is on. Displays without a serial fall back to the code alone, with a number for duplicates. Monitorian keys by device instance id, which changes with the port.
- **Matching WMI to a display** uses the PnP instance id derived from the device path (`DISPLAY\BOE0812\4&…&UID265988`), as both projects do.
- **Clone mode.** A GDI source can have several physical monitors and there is no documented order between them (Twinkle Tray). Handles that answer DDC/CI go to external targets in order, and a laptop panel never gets a DDC/CI handle.
- If `QueryDisplayConfig` fails, physical monitors are still listed under their dxva2 descriptions, and gamma falls back to `EnumDisplayDevices`.

## 2. Brightness controls

Each display gets one control class (`hardware/windows.py`), chosen in this order, after Monitorian's `MonitorManager` with Twinkle Tray's software fallback:

1. **DDC/CI** (`_VcpControl`) for external monitors that answer VCP `0x10`; the "high-level" `GetMonitorBrightness` (`_HighLevelControl`) only as a fallback, since it parses the capabilities string first.
2. **WMI** (`_WmiControl`) for built-in panels.
3. **SDR content brightness** (`_SdrControl`) for HDR displays without working DDC/CI.
4. **Software dimming** (`_SoftwareControl`) for anything else, unless turned off.
5. Otherwise listed as unsupported, with the reason and what to try.

The backend picks one per display and never branches on the kind again; every display's info says how it is controlled and why (`MonitorInfo.why`), shown in Settings > Displays and in the compatibility report.

### DDC/CI

- **Ranges** aren't always 0–100: values scale between the minimum and maximum the monitor reports.
- **Transient errors** (I2C and invalid-message errors `0xC0262582/83/86/89/8A/8B`) are retried: 3 attempts, 50 ms apart (Twinkle Tray's numbers).
- **"Monitor gone"** errors (`ERROR_GRAPHICS_MONITOR_NO_LONGER_EXISTS`, `INVALID_PHYSICAL_MONITOR_HANDLE`) become `MonitorGoneError` and trigger re-detection, at most once per 30 s.
- **Handles** stay open between calls and are destroyed on re-detection, never while a call that uses them is still running. A handle value of 0 is valid (Monitorian).
- **Spacing.** Messages to one monitor are at least 50 ms apart, as the DDC/CI standard asks.
- **What is written.** Only VCP `0x10`: when the user moves a slider, and for restores and the brightness schedule only after VCP `0xD6` says the monitor is on. Contrast, input switching and raw VCP codes are deliberately not offered: a wrong DDC/CI write can switch a monitor's input, turn it off or reset it.
- **Read-back.** `SetMonitorBrightness` can report success when the monitor ignored the change (Monitorian). Each display keeps its desired, commanded and observed level; it is read back once, 1.5 s after the last change, and a mismatch is logged once.
- **Planned:** falling back to VCP `0x13` or `0x6B` for monitors that ignore `0x10` (Twinkle Tray tries these); `--probe` already reports them. An update-rate setting, if a monitor flickers at the fixed 100 ms throttle.

### Laptop panels (WMI)

- Levels snap to the nearest level WMI reports. The slider stops at 1%: on some laptops 0 turns the backlight off.
- The `wmi` package (COM) is used; the WMIC command-line tool no longer ships with current Windows 11 (Twinkle Tray).
- COM is initialised on the thread that uses it, with one connection per thread, since calls can move to a fresh thread after a stuck one. The connection is released on its own thread (see §5, garbage collection).
- WMI fails transiently at sign-in and right after waking; a failed query is logged and the next detection tries again.
- Some laptops (OEM-controlled backlights, some OLED panels) expose no WMI brightness; they are listed as unsupported with that reason.
- **Planned:** Monitorian prefers the power plan's brightness setting (`PowerWriteACValueIndex`/`PowerWriteDCValueIndex`) so a level survives power-plan switches. Plain WMI until testing shows a need.

### HDR displays

- HDR state comes from `DISPLAYCONFIG_DEVICE_INFO_GET_ADVANCED_COLOR_INFO_2` on Windows 11 24H2 and later, where auto color management makes the older query report "advanced color" for SDR displays; the older query is the fallback. Which one works is learnt once.
- **SDR content brightness** (as Monitorian and Twinkle Tray 1.17 implement it): the documented get (type 11) and the undocumented set (type `0xFFFFFFEE`, flag byte 1), in thousandths of 80 nits, 80–480 nits mapped to 0–100%, rounded to 4 nits.
- **HDR monitors with DDC/CI.** Monitorian gives every HDR display SDR brightness before looking at DDC/CI; Twinkle Tray keeps DDC/CI and adds an SDR slider. Many monitors lock their backlight in HDR mode, so Winlight keeps DDC/CI while the monitor obeys it, and when a change is ignored (seen in the read-back) or refused twice, marks the display locked: the next detection releases its DDC/CI handle and switches it to SDR content brightness at the level asked for. The lock lasts while HDR stays on.
- **No automatic DDC/CI writes in HDR** (optional, per display). Twinkle Tray's maintainer traced a blue tint on one monitor in HDR mode (its issue #1310) to DDC/CI brightness changes then; the fix there was its SDR slider and skipping automatic changes. With the option, a display in HDR whose brightness goes over DDC/CI takes only the user's own slider: restoring the remembered level, the brightness schedule and following the laptop's keys pass it by (`MonitorManager.hands_off`). With HDR off, or brightness through Windows' SDR level, nothing changes.

### Software dimming

Twinkle Tray's driver-safe curve (`windows_display_brightness.cc`): a 20–100% range mapped to a 60–100% scale, the ramp's peak never below 70% (Windows rejects darker ramps), the exponent bending the curve below that so mid-tones still darken, always rebuilt from the display's base ramp so it never compounds. It saves no power and can't go as dark as a backlight. If Windows still refuses a level, the backend settles at the darkest level it accepts and logs it once.

## 3. Gamma ramps: night light, dimming and calibrations

Night light and software dimming share each display's one gamma ramp. As KWin composes brightness and color temperature into one transform per display (`ColorDevice::recalculateFactors`), `WindowsGammaBackend` keeps each display's **base ramp** (its calibration, or the identity) and recomposes base → dimming → idle dimming → tint whenever any layer changes, under a lock (night light changes come from the UI thread, dimming from the monitor thread). Gamma is per GDI source: cloned displays share one ramp. Displays in HDR mode are skipped, since Windows ignores gamma ramps there.

- **Windows' limit on warm ramps.** Windows refuses ramps far from neutral unless the `GdiIcmGammaRange` registry value is raised (DWORD `256` under `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\ICM`, the value f.lux's "expanded range" sets). The limit depends on the GPU, the display and any dimming. When a ramp is refused, the backend steps warmer until Windows accepts one, stays there, logs one warning, and remembers the limit for that display until the dimming changes. `core/colortemp.achievable_kelvin()` is the rule; Settings shows the limit under the night temperature ("3300 K (Windows limit)") while it holds a display back. The sleep recommendation asks for 2700 K and gets the warmest each display accepts.
- **Unlocking warmer colors** (`win32.expand_gamma_range`), as LightBulb does it (`RegistrySwitch`, `Reg.SetValue`): the value is set directly, which works when running as administrator, or else by Windows' own `reg.exe` (`reg add … /t REG_DWORD /d 256 /f`) through the administrator prompt (`ShellExecuteEx`, verb `runas`), waiting for it to finish. A declined prompt (`ERROR_CANCELLED`) changes nothing and is no error, as in LightBulb (its issue #335). Winlight differs in three ways: it offers this only while a limit actually holds a display back (LightBulb asks at every start until the value is set), it runs `reg.exe` by its full System32 path rather than whatever PATH finds, and it waits at most 60 s. Afterwards the limits found are forgotten and night light is applied again, so a limit that remains is found again; then Windows applies the value after signing out and in, or a restart, and Settings says so.
- **Verified writes.** Some drivers return TRUE without applying a ramp or keep fewer bits (Twinkle Tray). The ramp is read back and compared with a tolerance of 256.
- **Calibrations.** Windows loads a calibrated monitor's calibration into its ramp, and ramps outlive the app, so the ramp found on a display may be a calibration, Winlight's own tint from a crash, or another tool's tint. The journal (below) recognises Winlight's own tints exactly. Any other ramp is kept as the base if all channels peak at 90% or more, or if it curves like a calibration; it is rejected as a leftover tint only if it has a channel below 90% and every channel is a straight line, as a night light tint is. A calibration to a warm white point (D50, say) pulls blue to about 80% but curves, so it is kept. Before 0.3.0, the 90% peak alone decided, and such a calibration was replaced by a neutral ramp until Windows loaded it again.
- **Crash journal.** While a display is tinted or dimmed, its base ramp is journaled (`gamma.json`, per display identity), written at each switch between clean and tinted and periodically while tinted. At the next start, a ramp the journal recognises as Winlight's own (the last ramp written, or any tint of the base, for a crash mid-fade) gets its base back; a ramp Windows has reset meanwhile makes the entry stale, and it is dropped.
- **Keeping calibrations** (optional, off by default). Windows resets the ramp to a flat one when the screen turns off and on, dropping a calibration until its loader runs again, usually at the next sign-in. With the option on, a display's non-flat ramp is remembered, and a reset to flat is undone, with night light on top, as calibration loaders such as DisplayCAL's do. A new non-flat ramp (a re-calibration) is taken up.
- **Calibration status, reloading and forgetting.** Settings > Displays shows each display's calibration: in use, put back by Winlight (and how many times today), loaded from its profile, none detected, or none now but remembered. Windows' own loader (the `\Microsoft\Windows\WindowsColorSystem\Calibration Loader` task) can't be started by a standard user: its access list gives the Users group read and write, not execute. So **Reload** (`winlight-cli --calibration reload`) does what loaders do: it finds the profile Windows uses for the display (`WcsGetDefaultColorProfile`, per user or system-wide as `WcsGetUsePerUserProfiles` says, else `GetICMProfileW`), reads its calibration (`core/icc.py`) and puts it on screen, under night light. It reads the ICC `vcgt` tag (tables and formulas, written by DisplayCAL, ArgyllCMS and most calibrator software) and the curves of Windows' own Display Color Calibration in the profile's `MS00` tag when their gain is 1 and offset 0; how Windows combines a gain or offset with the gamma isn't documented, so those are reported, not guessed at. A profile with no calibration means none, which is how a calibration removed in Windows stops being put back. While "Use Windows display calibration" is off (`CalibrationManagementEnabled`), another program loads calibrations, and Reload leaves them alone. **Forget** (`--calibration forget`) drops the remembered copies. The first time a calibrated display is found with keeping off, a tray notification explains the option, once (`hints.json`).
- **Another program changing the ramp** (f.lux, a GPU color tool, a game). A single change is taken as the new base. Three changes within 30 s mean another program keeps doing it: that display is left alone for 2 minutes, doubling up to 30 minutes, with one warning, rather than flickering between the two.
- **Re-applying.** Windows resets ramps on the lock screen, after sleep and on display changes, often before saying so, and a driver can report the ramp it was last sent while the screen shows a reset one. After unlocking, waking, displays turning on and display changes, every ramp of Winlight's is set again at 0, 0.2, 0.6, 1.2 and 2 s whatever it reads back (`reapply()`, as LightBulb re-sets for 2 s after such an event), then checked at 3, 5, 8 and 12 s. Resets in the 15 s after the event are Windows', so they don't count as another program fighting over the ramp. `verify()` also runs every 1.5 s (one `GetDeviceGammaRamp` per display) and re-applies only where Winlight's ramp was replaced; with an honest driver it catches a later reset, such as the one LightBulb's #448 found when Quick Settings first opens, within 1.5 s. A driver that reports the ramp it was sent while the screen shows a reset one can only be corrected by setting it again, which the burst does; tests cover both. While the displays are off or the PC sleeps, the check runs every 30 s and the app in front is looked at every 10 s (LightBulb #419: no work while nothing is on screen); slower, not stopped, in case the "on" message never comes.
- **A nudge in every ramp.** Some drivers ignore a ramp identical to the last one they were sent, even after the screen's ramp was reset. Each tinted or dimmed ramp has its top entry lowered by 0 to 4 (of 65535), rotating, as LightBulb does (`DeviceContext.SetGamma`); that is invisible and well within the read-back tolerance. A display's own ramp, untinted, is always set exactly.

## 4. Schedules

- **Night light** follows custom times or sunset to sunrise at a location. Transitions follow knighttime's rules: by default the evening change runs from sunset to civil dusk and the morning change from civil dawn to sunrise; a fixed length instead starts at sunset and ends at sunrise. If the sun doesn't rise or set (polar day or night), or no location is set, 06:00 and 18:00 are used, as KDE does.
- **High latitudes** (`core/schedule._solar_day`). Each event is the moment the sun's elevation (astral's) passes its angle between one solar midnight and the next noon, found by bisection, independent of calendar dates. Before 0.3.0 Beta 2 the events came from astral's `sun()`, which gives up for a whole date when one event is missing or falls on the next date: in Reykjavik from May to July (the sun sets, but twilight never ends), and on single summer days in Stockholm and Helsinki when dusk came near midnight. Each made the whole schedule fall back to 18:00 and 06:00. Now a white night's dusk and dawn are solar midnight, its darkest moment (as LightBulb takes the closest point when the sun doesn't reach an angle, its fix for issue #132), and a fixed transition length ends there at the latest, so evening and morning never overlap. Tests sweep a year in Stockholm and Reykjavik for gaps, overlaps and jumps; the brightness schedule's sunrise and sunset come from the same calculation.
- **Brightness** (`core/brightness_schedule.py`, `brightness/scheduler.py`) has its own schedule: points at clock times or sunrise/sunset ± minutes (using night light's location), with an optional transition. Twinkle Tray's "time adjustments" apply the latest point at startup and when a newer one comes due; Winlight applies each point once per display, identified by the instant it began, and saves that identity, so a restart within a point leaves the level the user picked alone. Sleeping through several points applies only the latest. A display that wasn't reachable gets the level when it answers. While idle dimming holds the displays down, a point that begins waits until the user is back.
- **Time.** Points are laid out in the local zone (Qt's mapping of Windows' zone to an IANA name) and compared as absolute instants, so daylight saving changes neither skip nor repeat a point. A time zone change is followed from Windows' clock-change message and a check each minute.

## 5. Threading, time limits and failure handling

These rules shape `brightness/monitors.py`, `hardware/windows.py`, `hardware/calls.py` and `hardware/winsystem.py`. The races are tested step by step in `tests/test_monitor_service.py`, and all at once in `tests/test_chaos.py`.

- **One serialized queue.** The UI thread only asks; one worker thread makes every backend call in turn. A display's newest level replaces an older one not yet sent; detection requests close together are merged; a level the user just picked is never replaced by an unprompted one (a restore, the schedule).
- **Addressed by identity, never by position.** Commands carry the display's key and are resolved against the current detection when they run. A command for a display that disappeared, or whose port now has a different monitor, reaches nothing.
- **Time limits.** Detection 20 s, reads and writes 5 s, power state 3 s, the side-by-side DDC/CI probes 4 s. A call that doesn't return is abandoned; its display is left alone until the call returns (at most one stuck thread per display), and the others carry on. Quitting waits at most 3 s. Monitors that hang during detection are the main reason: Twinkle Tray 1.18 added a safer detection path for them.
- **Crash safe mode** (`system/safe_mode.py`, after Twinkle Tray 1.18's fallback to a safer method after a detection crash). A marker is written before each display's DDC/CI detection and removed after; one left at start means the app crashed or was ended during it, so that display's DDC/CI is skipped, with a reason in the panel, until ⟳ retries it.
- **Per-display failures.** Each display is detected, read and written in its own error handling; one display's gamma ramp failing doesn't stop the others.
- **The gamma lock is waited for only so long** (`hardware/windows._GammaLock`). Software dimming changes a ramp on the worker thread, under the gamma backend's lock. A driver call that hangs there is abandoned by its time limit, but its thread still holds the lock, and the UI thread's next night light change would have waited for ever. The lock is waited for at most 2 s, then 0.05 s until it is free again; the change is skipped (the next tick repeats it), one warning is logged, and Reload or Forget say why nothing happened.
- **Events after the lock.** The worker thread's events reach the UI thread through a queued signal. The one event raised on the caller's own thread (a restore or schedule level set aside for the user's) is sent after the service's lock is released, since its slots run at once and take other locks.
- **Desired, commanded, observed.** Each display's state records what the app wants, what the display last accepted and what it last reported, plus why it can't be changed now (detecting, reading, standby, asleep, not responding, retrying, disconnected). A slider is enabled only when a change can really be made; otherwise it says why.
- **ctypes.** `hardware/win32.py` and `hardware/winsystem.py` are the only modules that call native code. Every function declares its argument and return types (handles are pointers and would be truncated as `int`); structure sizes are checked against the SDK at start, and a feature whose layout is wrong is turned off rather than corrupting memory; optional APIs are detected once; nothing can escape a ctypes callback; errors are logged with their code, Windows' text and what they usually mean.
- **Garbage collection** (`system/gc_guard.py`). Python collects reference cycles in whichever thread allocates past a threshold. If the garbage holds Qt objects, collecting it on a worker thread destroys them off the main thread, and Qt crashes. Automatic collection is therefore off, and a main-thread timer collects instead. Nothing else may call `gc.collect()` (a test enforces it); worker threads create no Qt objects and send plain Python objects to the main thread through a queued signal; and objects tied to a thread, such as WMI's COM objects, have their cycles broken on that thread (`release_cycles()`) so reference counting frees them there.
- **Atomic files.** Settings and state are written to a temporary file and renamed over the old one, retried briefly while antivirus or the search indexer holds the file. An unreadable settings file is kept as `settings.json.damaged` before defaults replace it.

## 6. Sleep, displays off and hotplug

Sleep and hibernation cause most failures in apps like this: monitors vanish, handles go stale, monitors don't answer for a while after waking (Monitorian issue #50), and DDC/CI to a sleeping monitor can wake it or hang its firmware.

- **Notifications** (`hardware/winsystem.SystemEvents`, after Monitorian's `PowerManagement`). A hidden window receives suspend and resume (the two resume messages of one wake merged), displays off/on (`GUID_CONSOLE_DISPLAY_STATE`), lock and unlock (`WTSRegisterSessionNotification`), the laptop panel's brightness (`GUID_VIDEO_BRIGHTNESS`), `WM_DISPLAYCHANGE`, `WM_TIMECHANGE` and `WM_ENDSESSION`.
- **While asleep or off, nothing is sent to the displays.** After waking, commands wait for a fresh detection (old handles are stale), and the schedule re-evaluates.
- **Re-detection.** After display changes at 2 and 8 s; after the displays turn on at 3, 8 and 20 s; after waking at 2, 5, 10, 20, 30, 60 and 120 s, stopping once every display that answered before sleep has answered twice (`brightness/wake_report.py`, which logs each pass). Monitorian re-scans over about two minutes after its issue #50; Twinkle Tray waits 5–7 s after hardware changes. A detection that fails for a moment keeps the displays known before and tries again with growing gaps.
- **The watcher** (`system/watcher.py`) merges Qt's screen signals and Windows' messages into one signal per change once they settle, and acts at least every 5 s if a display keeps changing (a loose cable). It also covers the failures that leave an app stuck:
  - a sleep announced but never taken (cancelled or failed) sends no resume: if the clock checks keep running normally 90 s later, the watcher carries on as awake;
  - a missed "display on": input at least 2 s after Windows reported the displays off means they are on (the key or click that turned them off doesn't count);
  - a clock change mistaken for a wake: Windows' clock-change message re-baselines the check;
  - a wall-clock jump between checks notices a wake even without Windows' messages.
- **Monitors that answered before** are shown as "not answering yet" after waking, not told to turn DDC/CI on.

## 7. Pausing night light and dimming when idle

- **Pausing** (`color/exemptions.py`). f.lux's "disable for" list is a main reason people choose it. Gamma ramps belong to displays, not windows, so the display showing the app pauses and the others keep night light. The foreground window is checked every 0.4 s (`GetForegroundWindow`, `QueryFullProcessImageNameW`, its client area against `MonitorFromWindow`'s rectangle; a minimized or invisible window is ignored). The client area leaves out the title bar, as LightBulb measures it, so a maximized window doesn't count; nor does one that draws its own title bar (VS Code, a browser) while it is maximized with a caption (`IsZoomed`, `WS_CAPTION`), which matters with the taskbar hidden automatically, where a maximized window covers the whole monitor. Fullscreen video, borderless and exclusive games drop the caption, so they still count. Three independent switches: any fullscreen app; a list of apps; and an automatic mode for an app keeping the screen on (`CallNtPowerInformation(SystemExecutionState)` reporting `ES_DISPLAY_REQUIRED`, which video players, browsers playing video, call apps and presentations set), an exclusive-fullscreen Direct3D game or presentation mode (`SHQueryUserNotificationState`), and well-known color-critical apps. Windows doesn't say which app keeps the screen on, so the automatic pause goes to the display of the app in front.
- **Windows' own shell is never a fullscreen app** (`hardware/winsystem.py`). The window classes and processes are LightBulb's (`Window.IsSystemWindow`, `ExternalApplicationService`), compared without case: the desktop (`Progman`, `WorkerW`), the taskbars, Start, Alt+Tab and Task View (`ImmersiveLauncher`, `ImmersiveSwitchList`, `MultitaskingViewFrame`, `XamlExplorerHostIslandWindow`), `ForegroundStaging`, `ApplicationManager_DesktopShellWindow`, and `explorer.exe`, `ShellExperienceHost.exe` and `StartMenuExperienceHost.exe`. Added for Windows 11: the tray overflow's windows, and search, Quick Settings and notifications (`ShellHost.exe`), the touch keyboard and emoji panel, the lock screen and the snipping overlay. While that passing shell UI is in front, pausing stays as it was, so opening Start over a paused video doesn't flash night light on; the desktop ends a pause, and so does File Explorer, whose windows belong to `explorer.exe` too (for it, only the shell's window classes count). Store apps' windows belong to `ApplicationFrameHost.exe`; as in LightBulb, the app is the process of the frame's first child window from another process, so Photos or Media Player can be listed by their own names.
- **Never pausing late at night** (optional). None of the three switches pause night light from a chosen point (night light starting to warm, being fully on, or a set time such as bedtime) until the morning transition starts (`core/schedule.pausing_held()`), so a late video or game doesn't undo it. With night light always on, the custom times stand for evening and morning. It applies only while night light is on, and is asked only when something would pause.
- **Dimming when idle** (`brightness/idle_dim.py`). Idle is `GetLastInputInfo`, across the 32-bit tick wraparound its documentation warns about. It is held while an app keeps the screen on, a game runs exclusive fullscreen, Windows is in presentation mode, or an app from the user's list is in front. A window that merely fills the screen (a browser or an editor in fullscreen) doesn't hold it; Windows' own "busy" state counts any fullscreen window, so Winlight doesn't use it here. External displays dim in software through a separate idle layer of the gamma ramp, so idle cycles never write DDC/CI; the laptop panel dims through WMI, which saves power; HDR displays through their SDR level when that is their control, otherwise not at all. Dimming never brightens a display, and the first input brings every display back to the level it should have now (a schedule point that passed meanwhile included).

## 8. Windows integration

- **Start at sign-in** (`system/autostart.py`). The installer creates the current user's `HKCU\…\Run` value (its "Start Winlight when I sign in" task, ticked by default); the setting turns it on and off through Explorer's `StartupApproved\Run` switch, as Task Manager does; the app only reads both keys at start. An app that rewrites its own Run value is treated as malware making itself persistent by Microsoft Defender's behavior monitoring when the program is unsigned (`Behavior:Win32/Persistence.A!ml`). 0.1.0 Beta 5 rewrote the value at every start to keep the path current, and was quarantined on the test laptop for it. The app writes a Run value only when the user turns the setting on and none exists for this program (the portable zip, or the task unticked at install). The uninstaller removes both values.
- **One running copy** (`system/single_instance.py`). A second launch asks the running copy to show its panel over a per-user named pipe; the command line uses the same pipe. The pipe's access list (`QLocalServer::UserAccessOption`) has a single entry, full access for the current user's SID (checked on the test laptop), so other users can't connect. Its name is predictable, so a client also checks that the process serving the pipe runs as the same user (`GetNamedPipeServerProcessId` and the process token) before sending anything.
- **Windows Night Light.** Its state has no API; it is read from the CloudStore registry blob (undocumented; byte 18 is 0x15 when on and 0x13 when off, at both the older and the 24H2 location). An unknown format shows nothing rather than a false warning.
- **Focus.** Opening a window over an exclusive-fullscreen game can minimize it. While `SHQueryUserNotificationState` says busy or a fullscreen app is in front, Winlight doesn't open windows on its own (a second launch's panel, settings at sign-in). Opening it from the tray is never blocked.
- **Laptop brightness keys** are handled by the firmware and Windows, not passed to apps. `brightness/keys.py` follows the panel's level instead, from Windows' power-setting notification and a 2 s check, and sets external displays to match; changes the app made itself within 2 s are ignored as its own echo. No keyboard hook, which games' anti-cheat may flag.
- **Plugging in and unplugging** (optional, `brightness/power_source.py`). Windows' power plans keep one brightness for battery and one for mains power, and apply it to the built-in display when the power source changes (`GUID_ACDC_POWER_SOURCE`). Without the option, Winlight takes that for the user's change: the remembered level is forgotten, and external displays may follow it. With it, a change reported in the 3 s after the power source changed is Windows' own: it isn't followed, the panel is read again after 1 s, and the level from before (seen at least 1 s before the message, in case Windows' change came first) is put back after 2 s. Power plans themselves are left alone.
- **Data folder.** Settings, state and logs live in `%LOCALAPPDATA%\WinLight` (`config.data_dir()`). Before 0.3.0 the folder was `night-light`; the first start of a newer version renames it, so nothing inside changes. The log file is `Logs\WinLight.log` (rotated to `.1` and `.2`); its earlier name, `night-light.log`, is renamed at the same time, history included, and reports include a log of either name. If the rename fails (an older copy still has files open), the old folder is used for that run and the rename is tried again at the next start.

## 9. Diagnostics and privacy

- **Report a Problem** (`support/diagnostics.py`) saves a zip (summary, logs, settings, the compatibility report) to `%LOCALAPPDATA%\WinLight\Reports`, not to the Desktop, which OneDrive's folder backup often syncs to the cloud, and copies a summary to the clipboard. It sends nothing to the displays, so it is safe at any time. Zips are deleted after 7 days, and the clipboard is cleared after 10 minutes if it still holds the summary.
- **Privacy** (`support/privacy.py`). Reports are meant to be posted publicly. Every log line and traceback, and every file in a report, has the user name, computer name, home folder and email addresses replaced; display serials are shortened to their last four characters; and nothing writes coordinates, cities, time zones, custom display names, listed app names or command-line arguments. Report timestamps are in UTC.

## 10. Tray and flyout

- **Placement** (`ui/placement.py`). Monitorian's `StickWindowMover` aligns the flyout with the tray icon (`Shell_NotifyIconGetRect`) and falls back to the taskbar corner, since the icon rectangle is wrong on some Windows 11 builds and for icons in the overflow area. Winlight derives the taskbar edge from the screen's geometry against its available geometry, trusts the icon rectangle only inside the taskbar strip, and keeps Windows 11's 12 px gap.
- **Hiding.** The flyout hides when it loses focus; a show request within 0.3 s of hiding is ignored, so the click that closed it doesn't reopen it (Monitorian uses 0.2 s).
- **Fresh values.** Brightness may have changed through the monitor's own buttons, so the flyout re-reads it on opening, at most every 5 s.
- **Sliders** send at once and then at most every 100 ms while dragging, so the monitor follows the drag, and only a display's latest value is ever sent.
- **Opening without a flash.** Windows shows a new window before its first paint, which appears as a white frame in dark mode; windows open transparent and fade in after their first paint (`ui/reveal.py`).
- **No stray windows.** Qt opens a widget shown before it has a parent as a window of its own. In 0.3.0 Beta 1 and earlier, each settings row showed its description that way while the settings window was built, so its first opening flashed about 40 small windows over the screen and took about a second. Rows now show it once it sits inside them, and a test fails if opening the settings or the panel shows any other window.
- **Suspend.** As in KDE, the panel's Suspend button keeps night light off until it is clicked again (Resume), in the day too, so the evening doesn't turn it on; its arrow has the timed choices. The tray menu has the same toggle.
- **The preview note.** While a temperature slider is held, the whole screen shows that temperature, as KDE does. A note in the middle of the screen says so ("Night light preview", the temperature) and goes when the slider is let go. It never takes focus and lets clicks through (`WS_EX_NOACTIVATE`, `WS_EX_TRANSPARENT`, checked on the test laptop), so the app in front, and pausing for it, don't change.
- **Showing warmth** (`ui/day_ribbon.py`, `widgets.WarmthSlider`, `flyout.WarmthTile`). The day ribbon paints today in 10-minute steps from the schedule (`compute_state`), each step in `kelvin_color`: the white the gamma ramp makes at that temperature (`colortemp.whitepoint`), softened toward the window in dark mode. In Settings it shows the settings on the page, applied or not, and is worked out again only when they change. The temperature sliders' track uses the same colors under the style's own handle, and the panel's Night Light tile is tinted faintly by the temperature on screen now. Nothing here touches a display.
- **The 24-hour preview**, after LightBulb's cycle preview (`DashboardViewModel`): a pretend clock moves 5 minutes every 50 ms until a day has passed, and night light shows the settings in Settings at each moment, applied or not, through the same preview path and note as the sliders, the note giving the time. Like LightBulb's, it shows the schedule itself, without a Suspend or Activate in effect. Windows' timers make the 50 ms closer to 60, so a day takes about 19 s on the test laptop. It stops with Stop, when a slider is held, or when Settings closes.
- **Not planned:** brightness by scrolling over the tray icon (both projects have it): Qt's `QSystemTrayIcon` doesn't expose wheel events, and it would need a native event filter for the icon's messages.

## 11. External monitors and TVs

From Twinkle Tray's [display detection page](https://github.com/xanderfrangos/twinkle-tray/wiki/Display-Detection-&-Support-Issues), both projects' READMEs and issues, and reports from other DDC/CI tools:

| Situation | What helps | What Winlight does |
|---|---|---|
| DDC/CI off in the monitor's menu, or blocked by a picture mode | Turning it on (the most common cause in both projects' FAQs) | The "not supported" text says to turn DDC/CI on, then to try another cable or port |
| Hubs, converters, KVMs, MST and docks | Testing without them; HDMI and DisplayPort can behave differently | The same advice; DisplayLink displays get their own reason |
| TVs | Most consumer TVs have no DDC/CI | HDR displays without DDC/CI get SDR content brightness; others get software dimming |
| NVIDIA Surround, AMD Eyefinity | Not supported: several monitors appear as one | Not planned |
| Old GPU drivers, dock firmware | Updating them | Advice in the installer notes |
| A monitor answering other codes than `0x10` | Twinkle Tray tries `0x13` and `0x6B` | `--probe` reports them; **Planned** as a fallback |
| AMD's "Custom Colors" | Turning it off (Twinkle Tray's README) | It fights over the gamma ramp; Winlight backs off as from any other color tool |

## 12. Test laptop

Measurements and results on the test laptop: HP ZBook Studio G5, Windows 11 25H2 (build 26200), Intel UHD 630 and NVIDIA Quadro P1000, one built-in AUO panel (`AUO24ED`, eDP, no DDC/CI, WMI with 101 levels), no external monitor, HDR off.

- All structure layouts match the SDK; `QueryDisplayConfig`, both HDR queries, the SDR level query, dxva2 and GDI gamma calls work, without leaking handles or GDI objects over hundreds of calls.
- The panel's DDC/CI handle (value 0) answers every read with `0xC0262589`; invalid handles give `0xC026258C` on all dxva2 calls, which becomes "monitor gone". Not probing the panel over DDC/CI took detection from about 670 ms to about 25 ms.
- **Warmest night light accepted: 3280 K** (blue peaking at 0.50), well past the 70%-peak guess from Twinkle Tray's dimming limit, which applies to dimming every channel at once. With 20% dimming on top, the limit moves to 4400 K. Software dimming is accepted down to 20%.
- A Windows calibration (`CalibratedDisplayProfile-3.icc`, gamma curves from Windows' Display Color Calibration) was kept under night light, given back on quitting, and after a process killed mid-tint. The panel is now set to sRGB, which Reload reads as no calibration; the calibration profile's curves (gamma 0.79) read correctly too. Not tried yet: Reload with a profile chosen per user, or a `vcgt` profile from DisplayCAL.
- On the panel's driver, a nudged ramp is applied and reads back nudged, and the crash journal still recognises it.
- With the taskbar hidden automatically, a maximized VS Code covered the whole display and counted as fullscreen, so night light could pause and the settings could stay closed at sign-in; it no longer does. A Qt window in fullscreen and a borderless one covering the screen still count.
- WMI reads and writes leave no reference cycles; one WMI connection leaves 51 objects in cycles, COM objects among them, which are broken on their own thread at release.
- `tools/hardware_checks.py` repeats these checks on any Windows PC.
- **Not yet tried on real hardware:** external DDC/CI monitors, TVs, HDR displays, hotplug, linked sliders, the laptop-key follower.
